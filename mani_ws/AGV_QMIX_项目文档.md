# 多 AGV 协同调度系统 — 项目设计文档

> 最后更新：2026-05-22

---

## 一、项目背景

本项目为参赛项目，目标是构建一套多 AGV 协同货物搬运系统，在仿真环境中完成训练，并部署到实车进行边缘计算推理。比赛时间为 **2026年6月中旬**。

---

## 二、硬件平台

| 项目 | 参数 |
|---|---|
| AGV 数量 | 4 辆 |
| 车体类型 | 万向轮（全向移动） |
| 传感器 | 激光雷达 + 相机 |
| 机械臂 | 厂商配套机械臂（固定位置、固定角度抓取） |
| 车载计算 | Jetson NX（边缘计算） |
| ROS 版本 | ROS1 |

## 三、任务场景定义

### 3.1 场景描述

- 仓库中有 **10 个货架**，每个货架随机生成 **A 类、B 类或 C 类货物**
- 货物被取走后，货架立即**随机补货**（A/B/C，无限补货）
- 多辆 AGV 协同完成货物搬运：
  - 去货架取货（到达货架位置即视为取货成功）
  - 根据货物类型送往对应投递区（A → 投递区 A，B → 投递区 B，C → 投递区 C）
- AGV 之间**不能占用同一格**，需要避免碰撞

### 3.2 关键设计决策

**抓取仿真简化：** Gazebo 中机械臂物理抓取调试成本极高，且对验证多车协作算法没有本质帮助。采用**"到位即取货"**的简化逻辑，到达货架位置自动完成取货。实车上仍使用真实机械臂抓取。

## 四、整体架构

```
┌─────────────────────────────────────────────────┐
│              QMIX（高层决策）                    │
│                                                  │
│  输入：各车位置 + 携带状态 + 所有货架当前货物类型 │
│  输出：每辆车的下一个目标（去哪个货架或目标点）  │
│  触发：当某辆车完成当前任务时重新决策            │
└─────────────────────┬───────────────────────────┘
                      │ 目标点
┌─────────────────────▼───────────────────────────┐
│              A* 路径规划（低层导航）              │
│                                                  │
│  输入：当前位置 → 目标位置，其他车当前位置       │
│  输出：具体路径（逐格走），每步走一格            │
│  说明：已有成熟实现，直接复用                    │
└─────────────────────────────────────────────────┘
```

### 为什么 QMIX 不直接负责路径规划？

| 方案 | 训练难度 | 收敛时间 | Sim-to-Real | 1个月可行？ |
|---|---|---|---|---|
| QMIX 负责任务分配 + A* 导航 | 低 | 数小时 | 容易 | **可行** |
| QMIX 端到端控制路径 | 极高 | 数周 | 很难 | **不可行** |

A* 已有成熟实现，是宝贵资产，直接复用。QMIX 专注于**"谁去哪"**的任务分配决策。

## 五、QMIX 设计

### 5.1 状态空间与观测

**每个 agent 的局部观测（obs）：**
```
- 自身位置 (x, y)，归一化
- 自身携带状态：one-hot [无货, A类, B类]
- 其他每辆车的位置 (x, y) + 携带状态 one-hot
- 每个货架的当前货物类型：one-hot [A类, B类]（动态！每次取货后随机刷新）
- 每个货架的位置 (x, y)，归一化（固定）
```

**全局状态（state，仅训练时用于混合网络）：**
```
- 所有车的位置 + 携带状态
- 所有货架的当前货物类型
```

### 5.2 动作空间（离散）

每辆车在每次决策时选择：
```
动作 0～9：去货架 0～9
动作 10：去投递区 A
动作 11：去投递区 B
动作 12：去投递区 C
共 13 个离散动作（n_actions=13）
```

**决策时机（方案B）：** 只有当某辆车完成当前任务（到达货架或目标点）时，才触发 QMIX 为该车重新分配任务。

### 5.3 奖励设计

```
+10   成功将货物送到正确目标点
-2    送到错误目标点
-0.05 每个时间步的小惩罚（鼓励快速完成）
```

奖励为团队共享（所有 agent 获得相同 reward），这是 QMIX 协作学习的基础。

### 5.4 网络结构

- **AttentionAgentQNet**：双路注意力网络，参数在 4 台车间共享
  - 货架注意力：self_feat → Q，10 个货架 → K/V，输出货架上下文 (32维)
  - 车间注意力：self_feat → Q，其他 3 台车 → K/V，输出协作上下文 (32维)
  - 货架头：[self_feat(19) ‖ shelf_ctx(32) ‖ agent_ctx(32)] → Q(0..9)
  - 投递头：self_feat(19) only → Q(10..12)
- **MLPAgentQNet**：对照基线，两层 MLP（hidden=64）
- **QMixNet**：超网络（Hypernetwork）从全局状态生成混合层权重，取绝对值保证单调性（IGM 条件）

## 六、训练策略

### 6.1 为什么不在 Gazebo 里训练？

直接在 Gazebo 里训练 QMIX 是**不可行**的：

```
Gazebo 运行速度 ≈ 实时（1秒=1秒）
QMIX 需要训练 ≈ 数万个 episode
每个 episode ≈ 几分钟
总训练时间 ≈ 几个月（超出比赛时限）
```

### 6.2 正确的训练流程

```
第一阶段：纯 Python 2D 网格仿真训练（快！几小时收敛）
    ↓  策略迁移
第二阶段：接入 Gazebo 验证（修正 sim-to-real 差异）
    ↓  部署
第三阶段：Jetson NX 实车推理
```

### 6.3 2D 仿真环境设计

```
地图：10×10 网格
货架：4个，位置固定，货物类型动态随机
目标点：目标A、目标B，位置固定
AGV：2～3辆，每步走一格，不能同格
取货：到达货架格即取货，货架立即随机补货
```

## 附：关键设计取舍记录

| 问题 | 决策 | 原因 |
|---|---|---|
| 抓取仿真 | 到位即取货，不模拟物理抓取 | Gazebo 物理抓取调试成本高，对验证协作算法无本质帮助 |
| 训练环境 | 纯 Python 2D 仿真，不在 Gazebo 训练 | Gazebo 实时速度无法支撑 RL 训练所需的 episode 数量 |
| 路径规划 | A* 负责导航，QMIX 只做任务分配 | QMIX 端到端路径规划在1个月内无法完成调参 |
| QMIX 框架 | 手写 PyTorch，不用 PyMARL | PyMARL 框架复杂，出问题难调试，手写更可控 |
| 决策时机 | 任务完成时触发（非每步触发） | 更符合实际调度逻辑，动作空间语义更清晰 |
